# 日本株の中期リターン予測

## 1. 目的

本プロジェクトでは、機械学習を用いて東証上場の内国普通株式の短期〜中期的なリターンを予測し、銘柄の順位付けに利用する。

当面は、週初の情報から週末までの値動きを予測し、予測値が高い上位銘柄を保有するロングオンリー戦略を検証対象とする。単に予測誤差を小さくするだけでなく、取引コスト控除後に再現可能な運用成績が得られるかを確認する。

> [!IMPORTANT]
> 本プロジェクトは調査・学習を目的としたものであり、投資助言ではない。バックテストの成績は将来の成果を保証しない。

## 2. 設計上の決定

予測期間と決算発表の扱いには、次の方針を採用する。

1. **予測期間の定義**
   - 各週の最初の取引日の終値時点で特徴量を確定し、同じ週の最後の取引日の終値までのリターンを予測する。
   - 通常週の月曜終値から金曜終値までは、価格差分としては4営業日先である。本プロジェクトでは厳密な `t+5` ではなく、この同一週内の期間を予測対象とする。
2. **決算後25営業日の除外目的**
   - 保有中に決算を跨がないよう、エントリー日から決済日までに決算発表がある候補を除外する。
   - 決算直後の急変が特徴量に残ることを避けるため、決算発表後25営業日のクールダウンも適用する。
   - クールダウンはサンプル数を大きく減らす可能性があるため、主結果とは別に適用あり・なしの感度分析も行う。

## 3. 予測・売買タイミング

「学習日」と「テスト日」という表現はデータ分割と混同しやすいため、以下の名称を使う。

- **シグナル日 `t`**：各暦週の最初の取引日。通常は月曜日、月曜日が休場なら火曜日。
- **評価日 `e(t)`**：同じ暦週の最後の取引日。通常は金曜日、金曜日が休場なら木曜日。
- シグナル日または評価日が上記以外になる週、取引日数が極端に少ない週は原則として対象外とする。具体的な最低取引日数は設定ファイルで管理する。
- 特徴量はシグナル日 `t` の取引終了時点までに得られる情報だけで作る。
- 終値を見てから同じ終値で約定することはできないため、**予測精度の検証**と**売買バックテスト**を分ける。
  - 予測精度：シグナル日の調整済み終値から評価日の調整済み終値までを評価する。
  - 売買バックテスト：シグナル計算後の次の取引日の始値で買い、あらかじめ定めた決済価格で売る。決済価格は「評価日の終値」または「評価日の翌取引日の始値」のどちらかに固定する。

## 4. データセット

### 4.1 データソース

[J-Quants API](https://www.jpx.co.jp/markets/other-data-services/j-quants-api/)から、少なくとも次のデータを取得する。

- 株価四本値：日次のOHLC、出来高、売買代金、調整係数、調整済みOHLC・出来高
- 上場銘柄一覧：銘柄名、市場区分、業種、上場・上場廃止の判定に必要な情報
- 取引カレンダー：東証の営業日
- TOPIX四本値：市場相対リターンの計算に使用
- 決算発表予定日および財務情報の開示日：決算跨ぎの除外判定に使用

J-Quantsでは調整前と調整済みの株価データが提供される。価格リターンとテクニカル特徴量には原則として調整済み系列を使用し、売買代金や約定可能性の判定には元の値との意味の違いを確認して使用する。

現在の `data/raw/` には2016年から2026年までの年別Parquetがあるが、2016年と2026年は通年データとは限らない。各実験では、ファイル名ではなく実データの最小日・最大日、行数、銘柄数を記録する。

### 4.2 投資対象ユニバース

各シグナル日時点で次の条件を満たす銘柄を候補とする。

- その日時点で東証に上場している内国普通株式
- ETF、ETN、REIT、インフラファンド、優先株、外国株などは除外
- 上場後60取引日以上経過している
- 直近の価格・売買代金・取引日数が流動性条件を満たす
- シグナル日と予定決済日に売買可能な価格が存在する
- 監理・整理銘柄、長期売買停止銘柄などは、取得可能な情報に応じて除外する

現在上場している銘柄だけから過去のユニバースを作らない。各時点の上場銘柄一覧を用い、上場廃止銘柄も含めることで生存者バイアスを避ける。市場区分変更、銘柄コード変更、合併、上場廃止についても時点整合性を保つ。

### 4.3 データの保存と再現性

- `data/raw/`：取得した原データを原則として変更せず保存する。
- `data/interim/`：型・列名・取引日などを整えた中間データを保存する。
- `data/processed/`：学習に使用する特徴量、目的変数、ユニバース判定を保存する。
- API取得日時、取得範囲、APIまたはスキーマのバージョン、入力ファイルのハッシュを記録する。
- APIキーや認証情報はリポジトリに保存しない。
- 再取得によって過去データが訂正される可能性があるため、実験ごとに入力データのスナップショットを識別できるようにする。

## 5. 前処理と品質検査

### 5.1 基本処理

- 日付と銘柄コードの組を主キーとし、重複行がないことを確認する。
- 営業日は個別銘柄の観測行ではなく、東証の取引カレンダーを基準にする。
- 市場休場日の行は作らない。
- 株式分割・併合の影響はJ-Quantsの調整済み系列と調整係数を用いて処理する。
- 特徴量は銘柄ごとに日付昇順で計算し、別銘柄の値が混ざらないようにする。
- 無限大、ゼロ除算、不正な負値、異常なリターンを検出し、件数と処理内容をログに残す。

### 5.2 OHLCVの整合性

価格が存在する行では、少なくとも次を検査する。

```text
Low <= Open <= High
Low <= Close <= High
Volume >= 0
TurnoverValue >= 0
```

違反行を機械的に修正せず、原データの確認対象として隔離する。調整済みOHLCについても同様の関係を確認する。

### 5.3 欠損値と無取引日

株価を前日値で補完すると、実際には売買できなかった日に架空の約定価格を作るため、原則としてOHLCを前方補完しない。

- 市場は開いているが当該銘柄に価格がない日は「欠損」または「売買なし」として保持する。
- シグナル日または決済日の価格が欠損しているサンプルは使用しない。
- 特徴量の計算に必要な履歴が不足するサンプルは使用しない。
- 直近20営業日に価格形成があった日数の下限を設け、売買停止や無取引が多い銘柄を除外する。
- 欠損率は日付別・銘柄別・列別に集計し、除外後の銘柄数とともに記録する。

### 5.4 流動性フィルタ

出来高は株価水準によって比較しにくいため、主指標には売買代金を使う。閾値は未確定のため設定ファイルで管理し、開発期間だけで決定する。

- 例：直近20取引日の売買代金中央値が一定額以上
- 例：直近20取引日のうち、価格形成のある日が一定数以上
- 例：予定投資額が直近売買代金の一定割合を超えない

当日の売買代金で当日の始値に約定できるかを判定するなど、実際の発注時点で未知の情報をフィルタに使わない。

### 5.5 決算発表の扱い

- 保有予定期間 `(シグナル確定時刻, 決済時刻]` に決算発表が予定されている銘柄は候補から除外する。
- 予定日だけでは発表日の変更や予定外の発表を捉えられないため、実績の開示日でも事後検証する。
- 決算発表時刻を利用できない場合、発表日は保守的にイベント日として扱う。
- 決算後25取引日のクールダウンを適用し、補助分析として適用あり・なしの両方を比較する。

## 6. 目的変数

### 6.1 回帰ターゲット

シグナル日 `t` の調整済み終値を `P(i,t)`、同じ週の評価日を `e(t)` とし、銘柄 `i` の単純リターンを次のように定義する。

```text
y(i,t) = P(i,e(t)) / P(i,t) - 1
```

銘柄固有の上昇余地を学習しやすくするため、TOPIXの同期間リターンを引いた超過リターンも比較対象とする。

```text
y_excess(i,t) = y(i,t) - y_TOPIX(t)
```

最終的に上位銘柄を選ぶことが目的であるため、日付ごとのリターン順位または標準化リターンを目的変数にした学習も比較する。ターゲットの選択は2025年以降の最終バックテストを見ずに決定する。

### 6.2 ラベル作成上の注意

- 目的変数が欠損する直近期間は学習・評価から除外する。
- 上場廃止直前の銘柄を単純に欠損として捨てると上方バイアスが生じるため、最終売買日や上場廃止時の扱いを別途定義する。
- ストップ高・ストップ安、売買停止などで理論上の価格に約定できない場合は、予測評価と売買評価で扱いを分ける。

## 7. 特徴量

すべての特徴量はシグナル日の取引終了時点までのデータだけから計算する。価格 `P` には調整済み終値、日次リターンには原則として対数リターンを使う。

| 特徴量 | 暫定定義 | 意図 |
|---|---|---|
| `R_5` | `P_t / P_(t-5) - 1` | 短期モメンタム |
| `R_20` | `P_t / P_(t-20) - 1` | 約1か月のモメンタム |
| `R_60` | `P_t / P_(t-60) - 1` | 約3か月のモメンタム |
| `PriceToSMA_20` | `P_t / SMA_20 - 1` | 20日移動平均からの乖離 |
| `SMA_5To20` | `SMA_5 / SMA_20 - 1` | 短期・中期トレンド |
| `Volatility_5To20` | `Volatility_5 / Volatility_20` | 短期的な変動率上昇 |
| `Volatility_20` | 日次対数リターンの20日標準偏差 | 直近の価格変動率 |
| `RangePosition_20` | `(P_t - Low_20) / (High_20 - Low_20)` | 20日レンジ内の位置 |
| `VolumeRatio_5To20` | `MeanVolume_5 / MeanVolume_20` | 出来高の増減 |
| `TurnoverRatio_5To20` | `MeanTurnover_5 / MeanTurnover_20` | 売買代金の増減 |
| `RelativeTOPIX_20` | `R_20 - R_TOPIX_20` | 市場に対する相対強度 |

`High_20 == Low_20`、分母がゼロ、履歴不足の場合は欠損とし、学習直前に一貫した規則で処理する。`Vol` が価格変動率と出来高のどちらを表すか曖昧にならないよう、列名には `Volatility` または `Volume` を明記する。

追加候補として、市場・業種中立化したリターン、ATR、ギャップ、売買代金順位、時価総額、曜日・月、相場レジームを検討する。ただし特徴量を増やすたびに、追加理由とアブレーション結果を記録する。

### 7.1 外れ値処理と標準化

- 外れ値の上下限は学習期間だけから推定するか、各シグナル日の銘柄横断順位に変換する。
- 時系列方向の標準化器・欠損補完器は学習データだけで `fit` し、検証・テストには `transform` のみを行う。
- 日付横断の順位化や標準化は、その日に投資可能なユニバースだけを使う。
- 前処理をモデル選択の外側で全期間に一括適用しない。

## 8. 学習・検証・最終評価

### 8.1 データ分割

- 同じシグナル日の全銘柄を必ず同じ分割に入れる。銘柄単位のランダム分割は行わない。
- **開発期間**：制度上の境界は2016年〜2024年。学習、特徴量選択、閾値決定、ハイパーパラメータ調整に使用する。
- **最終バックテスト期間**：2025年〜2026年。設計確定後に一度だけ最終評価する。ただし2026年は、目的変数まで確定している最終日までに限定する。
- 現在の10年スナップショットは2016-11-01開始のため、2016-11-01〜2017-02-03をウォームアップ専用とし、最初の分析シグナルを2017-02-06とする。開始日前の原データは `R_60`、上場履歴、流動性、決算クールダウンの計算にだけ使う。

開発期間では、時系列順を維持したウォークフォワード検証を行う。例として、過去データで学習し、その直後の1年で検証する拡大型の分割を使う。

```text
学習: 2017-02-06〜2019  -> 検証: 2020
学習: 2017-02-06〜2020  -> 検証: 2021
学習: 2017-02-06〜2021  -> 検証: 2022
学習: 2017-02-06〜2022  -> 検証: 2023
学習: 2017-02-06〜2023  -> 検証: 2024
最終学習: 2017-02-06〜2024 -> 最終バックテスト: 2025-2026
```

学習期間末のラベル計算に検証期間の価格が入らないよう、目的変数の予測期間に応じたパージ期間を設ける。最終バックテストの結果を見て特徴量や閾値を変更した場合、それは最終評価ではなくなったものとして新たな未使用期間で再評価する。

### 8.2 比較するモデル

まず単純な基準を作り、複雑なモデルが本当に改善しているかを確認する。

- 定数予測または前週リターンを用いたナイーブ予測
- 線形回帰、Ridge、Elastic Net
- 決定木系モデル（Random Forest、勾配ブースティングなど）
- 必要に応じてランキング学習

各モデルは同じ分割、同じユニバース、同じコスト仮定で比較する。ニューラルネットワークは、データ量と基準モデルに対する改善余地を確認してから検討する。

### 8.3 予測性能の評価指標

- MAE、RMSE
- 方向一致率
- 日付ごとのPearson相関およびSpearman順位相関（Information Coefficient）
- 上位N銘柄の平均実現リターン
- 上位群と下位群のリターン差
- 年別、相場局面別、業種別、時価総額別の安定性
- 予測可能な銘柄の割合（coverage）

平均値だけでなく、日付ごとの分布、標準誤差、外れ週への依存度も確認する。

## 9. ポートフォリオ構築とバックテスト

### 9.1 銘柄選択

- 各シグナル日に、投資可能ユニバースを予測値の降順に並べ、上位N銘柄を選択する。
- 当初は等金額配分を基準とする。
- 1銘柄当たりの上限、業種集中上限、同時保有銘柄数、最低現金比率を設定可能にする。
- 予測値が取引コストを上回らない場合に取引を見送るルールも比較する。
- 株数は売買単位と利用可能資金を考慮して整数に丸める。

### 9.2 現実的な約定条件

バックテストには少なくとも次を反映する。

- 売買手数料、スプレッド、スリッページ
- 売買代金に対する参加率上限
- 制限値幅、売買停止、出来高不足による未約定
- 配当、株式分割・併合、上場廃止
- 注文から約定までの1営業日以上のラグ
- 銘柄入れ替えに伴うターンオーバー

コスト0の結果を参考値、保守的なコストを加えた結果を主結果として報告する。資金量を変えた容量分析も行う。

### 9.3 運用評価指標

- 累積リターン、年率リターン
- 年率ボラティリティ、Sharpe ratio
- 最大ドローダウン、Calmar ratio
- 勝率、損益比、週次リターン分布
- ターンオーバー、取引回数、平均保有期間
- TOPIXに対する超過リターン、tracking error、information ratio
- 銘柄・業種への集中度

## 10. 実験管理とリーク防止

- 実験ごとにデータ期間、特徴量、ユニバース条件、モデル、乱数シード、コスト仮定、コードのバージョンを保存する。
- 特徴量や目的変数の各列について、「その値が実際に利用可能になる日時」を意識する。
- 財務情報を追加する場合、決算期ではなく公表日時を基準に結合し、公表前の値を使わない。
- 全期間で算出した統計量、将来の上場区分、将来判明する決算日、最終バックテストの結果を学習や調整に使わない。
- 学習データと評価データの行数、日付範囲、銘柄数、欠損率を毎回出力する。
- 主要結果にはモデルだけでなく、ユニバース定義と取引コストの感度分析を添える。

## 11. 実装ロードマップ

1. データ辞書とスキーマ検査を作る。
2. 日次株価、銘柄マスター、取引カレンダー、TOPIX、決算日を時点整合的に結合する。
3. 欠損・異常値・上場廃止を含むデータ品質レポートを作る。
4. シグナル日、評価日、ユニバース、目的変数を生成する。
5. 特徴量を生成し、未来情報が混入していないことを単体テストする。
6. ナイーブ予測と線形モデルでウォークフォワード検証を行う。
7. 木系モデルを追加し、特徴量とモデルの寄与を比較する。
8. 約定ラグ、コスト、流動性制約を含むバックテストを実装する。
9. 2025年以降の期間で最終評価し、再現可能なレポートを出力する。

## 12. 完了条件

本プロジェクトの最初のマイルストーンは、次をすべて満たすこととする。

- 同一入力と同一設定から、特徴量・学習結果・バックテスト結果を再生成できる。
- データリーク、生存者バイアス、欠損値、上場廃止銘柄の扱いがテストされている。
- 単純な基準モデルを含む複数モデルが、同一条件で比較されている。
- 予測指標と取引コスト控除後の運用指標が、全期間および年別に報告されている。
- 最終バックテスト期間がモデル選択から隔離されている。

## 13. J-Quants API V2からの原データ取得（実装済み）

`data_download.py`、`auxiliary_data_download.py`、`preprocessing.py`、`descriptors.py` を
CLIまたはNotebookから実行する
コピー可能な例は [実行手順書](docs/RUNBOOK.md) にまとめている。

`src/stock_prediction/data_download.py` は、実行時にJ-Quants API V2のAPIキーを受け取り、
指定期間の取引カレンダーと全銘柄の日次株価を `data/raw/` 配下の新規スナップショットへ
保存する。CLIとNotebookは同じ `download_jquants_raw` を使用する。

現行V2の認証は `x-api-key`、株価は `/v2/equities/bars/daily`、カレンダーは
`/v2/markets/calendar` を使用する。カレンダーは閉場日を含む全暦日を取得し、
`HolDiv` が `"1"`（営業日）または `"2"`（東証半日立会）の日だけ株価を取得する。
全ページを `pagination_key` で追跡する。公式仕様は
[株価日足](https://jpx-jquants.com/ja/spec/eq-bars-daily)、
[取引カレンダー](https://jpx-jquants.com/ja/spec/mkt-cal)、
[ページネーション](https://jpx-jquants.com/ja/spec/pagination)を参照。

`JQUANTS_API_KEY` が未設定の場合だけ非表示プロンプトが出る。キーはソース、設定、ログ、
Parquet、manifestへ保存しない。開始日・終了日は両端を含み、契約プランで利用できる


```powershell

```

既定の5リクエスト/分はFreeプラン向けの保守値で、ページネーションも1リクエストとして
数える。契約上限に合わせる場合だけ `--requests-per-minute` を変更する。長期間を取得する前に
数営業日で接続、契約期間、スキーマ、出力を確認する。HTTP 429は既定65秒待って再試行し、
認証・契約・スキーマのエラーは黙って空データに置き換えない。

出力例は次のとおり。実行IDまたは `--output-dir` のディレクトリは新規でなければならず、
既存原本を上書きしない。manifestには取得日時、要求期間、API版、完了日、行数、銘柄数、
日付範囲、列別欠損率、重複数、SHA256、ライブラリ版を記録する。

```text

  trading_calendar.parquet
  prices/YYYY.parquet
  partial_prices/YYYY.parquet  # 中断・失敗した当年に取得済み行がある場合だけ
  manifest.json
```

途中で例外または `KeyboardInterrupt` が発生した場合も、完了年と取得済み当年データ、
失敗状態を可能な限り保存してから例外を再送出する。同じスナップショットへの自動再開はせず、
再取得は新しい出力先で行う。強制終了や電源断ではメモリ上の当日分まで保存できない場合がある。

## 14. 日次株価の前処理（実装済み）

`src/stock_prediction/preprocessing.py` は、`data/raw/YYYY.parquet` を年ごとに読み、
日付・銘柄コード・数値型の整形、主キー重複、未調整/調整済みOHLCの整合性、
非有限値・負値・欠損の検査を行う。不正行は理由付きで隔離し、価格は補完しない。
原本の必須16列、`MktCap` / `ExRT`、既知の前場・後場列、単位、追加監査列は
[データ辞書](docs/DATA_DICTIONARY.md) を参照。前処理の中核は必須16列だけを使い、
既知の任意列は型・値を検査して原本に残すが中間データへ複製しない。
実装判断と検証結果は [実装計画](docs/IMPLEMENTATION_PLAN.md) に記録する。

これは **観測行の中間データ** を作る工程である。内国普通株式の歴史的ユニバース、
決算除外、流動性フィルタ、週次ラベル、特徴量は後段で別途実装する。
全欠損行を保持するが、存在しない銘柄/日付の行は追加しない。ZIP内の株価は年別Parquetと
期間・スキーマが異なるため、自動混合・展開しない。

提供された調整済み価格は後日のコーポレートアクションで遡及変更され得る。
入力スナップショットを保持・識別し、調整済み絶対水準を当時利用可能だった特徴量とは
認定しない。研究の予測期間や目的変数の定義は変更しない。
学習用データを作る段階で調整基準と時点整合性を確認する。

### 環境とCLI

プロジェクトルートで実行する。Python 3.10以上が必要。

```powershell

python -m stock_prediction.preprocessing --help
```

既存の年別原データには取引カレンダーがない。カレンダーなしの暫定監査は明示的な
`--allow-unverified-calendar` を必要とし、全出力行とレポートに未検証状態を残す。
平日や株価観測日から営業日を推定しない。まず小さな期間を実行する例：

```powershell

```

`reports/preprocessing_<UTC実行ID>/` に保存する。既存ディレクトリは上書きしない。
全期間を整形する場合は日付引数を省略する。これは期間全体への統計量fitやモデル選択を行わない。

カレンダーを用意した後は、`Date` / `HolDiv` の2列を持つCSVまたはParquetを
`--calendar data/raw/trading_calendar.parquet` で渡す。対象期間の全暦日（閉場日を含む）が必要。
`HolDiv` の `"1"` / `"2"` を東証営業日とし、閉場日の株価行は隔離する。

出力には年別Parquet、`quarantine/` の隔離行、年別JSON監査結果、
日付別・銘柄別欠損率Parquet、`manifest.json` が含まれる。
manifestは入力SHA256、実日付範囲・行数、設定、コードSHA256、Git版（利用可能な場合）、
ライブラリ版、UTC実行日時、完了した年を記録する。取得日時/API版が原本にない場合は不明とする。
中断・処理失敗時も完了済みファイルと進捗を残す。

## 15. 日次テクニカル特徴量（実装済み）

## 16. 補助原データ取得（実装済み）

`src/stock_prediction/auxiliary_data_download.py` は、日次株価と同じJ-Quants API V2認証・
ページネーション・レート制御を使い、次の原データを新規の不変スナップショットへ保存する。

- [TOPIX日足](https://jpx-jquants.com/ja/spec/idx-bars-daily-topix)：
  `/v2/indices/bars/daily/topix`
- [過去時点の上場銘柄一覧](https://jpx-jquants.com/ja/spec/eq-master)：
  `/v2/equities/master` を東証営業日ごとに日付指定
- [決算発表予定](https://jpx-jquants.com/ja/spec/fin-earnings-date)：
  `/v2/fins/earnings-date` を公表日ごとに日付指定
- [決算実績・その他の財務開示](https://jpx-jquants.com/ja/spec/fin-summary)：
  `/v2/fins/summary` を開示日ごとに日付指定

決算予定と財務開示は休日の公表を暗黙に除外しないため、取引日だけでなく要求範囲の全暦日を
問い合わせる。列、型、要求日、主キー、TOPIXのOHLCと営業日coverageを保存前に検査し、
未知列や必須列欠落は早期エラーにする。APIキーは保存せず、出力先は既存ディレクトリを拒否する。
年別の完了状態、行数、銘柄数、日付範囲、欠損率、重複数、SHA256をmanifestへ記録し、
通常の例外または中断時も完了済み年と取得済み当年の部分データを可能な限り残す。

`/v2/fins/summary` は金額・株数・比率を含む全項目をJSON文字列で返し、未記載値を空文字列で
返す。財務サマリーrawではこれらの値を文字列のまま保存し、空文字列をNullやゼロへ置換しない。
数値化は、列ごとの単位・精度・欠損規則を定めた後続の監査済み前処理で行う。開示日・対象期間の
日付列だけは、要求日との一致と日付妥当性を検査するため日時型へ正規化する。manifestの欠損率では
保存値を変えずに空文字列も欠損として数える。

銘柄マスターの連続スナップショットから、コードの出現・消失・属性変更を
`master_transitions/` に保存する。ただし、出現・消失だけで新規上場・上場廃止・合併を確定しない。
同じ境界で消失・出現したコードの会社名が一意に完全一致する組は
`code_change_candidates/` に保存するが、銘柄マスターには旧新コードを結ぶ安定IDがないため、
**確認済みコード変更ではない**。最初の取得営業日は比較元のないbaselineであり、確定した
上場廃止・コード変更・合併等が必要な工程では別の公式コーポレートアクション情報で照合する。

CLIとNotebookは同じ `download_auxiliary_data` を使用する。長期取得は多数のAPI呼び出しに
なるため、まず短期間で契約プラン、取得可能期間、schemaを確認する。コピー可能なコマンド、
データセット単位の取得、中断時の確認、Notebook例、出力構成は
[実行手順書](docs/RUNBOOK.md) を参照する。

## 17. 時点整合ユニバース（実装済み）

`src/stock_prediction/universe.py` は、取引日別の銘柄マスターを主表として、各時点の
東証上場内国普通株式（`ProdCat == "011"`）、上場後60取引日、流動性、シグナル日の価格形成を
判定する。現在の上場銘柄を過去へ遡及適用せず、価格がない日もマスター行を残して20取引日窓の
欠損として数える。上場履歴、rolling、売買代金中央値は銘柄境界と上場区間を跨がない。

既定の流動性条件は、シグナル日を含む直近20取引日中15日以上の価格形成、未調整売買代金中央値
1億円以上、1銘柄100万円、参加率上限1%で、`configs/universe.json` に保存する。入力開始日に
すでに存在する銘柄も60取引日の経過を入力内で確認するまで除外し、消失・再出現時は履歴を戻す。

任意の週次スケジュールを渡すと、翌取引日始値での買いと同週評価日終値での売りについて、
価格、出来高、売買代金、ストップ高・安フラグから保守的な `is_executable` を生成する。
これは将来情報を使う事後proxyなので、シグナル時点の `is_eligible` から分離している。
監理・整理指定、板情報、実際の約定は現行入力から確定できず、決算除外も後続工程で扱う。

CLIとNotebookの実行例は [実行手順書](docs/RUNBOOK.md)、全入出力列、数式、欠損規則、
制限は [ユニバースデータ辞書](docs/UNIVERSE.md)、実装判断と検証結果は
[実装計画](docs/IMPLEMENTATION_PLAN.md) を参照する。

## 18. 決算跨ぎ除外と決算後クールダウン（実装済み）

`src/stock_prediction/earnings_events.py` は、週次候補の `signal_date` / `code` / `exit_date`、
J-Quantsの決算発表予定、財務サマリーの実績開示、公式取引カレンダーから、決算イベント除外を
生成する。Notebook用DataFrame API `compute_earnings_exclusions` と年別CLI
`stock-earnings-events` は同じ中核処理を使い、入力と `data/raw/` を変更しない。

主判定 `is_earnings_eligible` は、シグナル日までに公表済みの最新予定だけを使った決算跨ぎ除外と、
シグナル確定時刻までに実際に開示された決算短信から数えた25取引日のクールダウンを組み合わせる。
予定変更は `PubDate` より前へ遡及適用しない。予定データには発表時刻がないため、予定日が
シグナル日と同日の場合も保守的に跨ぎとして扱う。同じ銘柄・四半期・決算期末・公表日に複数の
予定状態がある場合は同日中の順序を推測せず集合として保持し、既知の候補日のいずれかが保有期間へ
入れば決算イベント1件として除外する。Null予定日を含む有効集合は監査列とレポートへ残す。

財務サマリーには業績・配当予想修正等も含まれるため、既定では実データで確認した `DocType` の
`1QFinancialStatements` / `2QFinancialStatements` / `3QFinancialStatements` /
`FYFinancialStatements` / `OtherPeriodFinancialStatements` 接頭辞だけを実績決算イベントとする。
未設定の `FinancialStatements` 系が現れた場合は黙って除外せずschema errorで停止する。発表日の次の東証取引日を1日目とし、
同日開示は東証大引け（2024年11月5日より前は15:00、同日以後は15:30）までなら0日目として
除外し、その後1〜25日目も除外、26日目から候補へ戻す。クールダウンなしの感度分析は
`is_earnings_eligible_without_cooldown`、保有期間中の実績開示も加味する事後監査は
`is_earnings_eligible_ex_post` として分離し、将来の実績開示を主判定へ混ぜない。

実データ件数・coverageは、入力スナップショットと実行結果のmanifestで確認する。実行例は
[実行手順書](docs/RUNBOOK.md)、列定義と境界は
[決算イベントデータ辞書](docs/EARNINGS_EVENTS.md)、実装判断と検証結果は
[実装計画](docs/IMPLEMENTATION_PLAN.md) を参照する。

## 19. 週次日程・目的変数・学習候補表（実装済み）

`src/stock_prediction/weekly_dataset.py` は、公式取引カレンダーから週次日程を作り、調整済み終値間の
単純リターン、同期間TOPIXリターン、TOPIX超過リターンを生成する。既定の最低取引日数は、
ユーザー確認済みの4日で `configs/weekly_dataset.json` に保存した。月曜から日曜まで確認できる
完全な暦週のうち、最初の取引日が月曜または火曜、最後の取引日が木曜または金曜の週だけを採用する。
同じ設定の `signal_start_date=2017-02-06` より前の週は監査理由を残して分析日程から外すが、
元の日次行は60取引日の特徴量・上場履歴等のウォームアップとして保持する。

週次ユニバースを主表に、日次特徴量と決算判定を `(signal_date, code)` で検査付き結合する。
決算キーはユニバースとの完全一致を必須とし、ユニバース合格行に特徴量行または調整済みシグナル日
終値がなければ工程間不整合として停止する。個々の特徴量欠損は後続の学習fold内処理のため保持し、
評価日価格欠損も補完・黙示除外せず理由と件数を残す。

シグナル時点の主判定 `is_signal_eligible` は `is_eligible and is_earnings_eligible` だけで作り、
将来情報を含む `is_executable`、`is_earnings_eligible_ex_post`、目的変数の観測可否を混ぜない。
学習可能性は `is_target_return_sample` と `is_target_excess_return_sample` に分離した。単純リターン、
超過リターン、日付横断順位のどれを最終ターゲットにするかは、2025年以降を使わず後続の
開発期間内比較で決定する。

Notebook用の `build_weekly_schedule` / `build_weekly_dataset` と、日程生成・年別結合の2サブコマンドを
持つCLI `stock-weekly-dataset` は同じ中核ロジックを使う。CLI例と実行順は
[実行手順書](docs/RUNBOOK.md)、全列・数式・欠損規則・制限は
[週次学習表データ辞書](docs/WEEKLY_DATASET.md)、判断と検証結果は
[実装計画](docs/IMPLEMENTATION_PLAN.md) を参照する。

現在の実データには、時点銘柄マスター、決算予定・実績、生成済み特徴量、週次ユニバースが
揃っていないため、実データ学習表の生成とcoverage評価は未完了である。合成データによる実装検証と、
公式カレンダーによる週次日程監査を、投資成績評価とは区別する。

## 20. パージ付きウォークフォワード分割と最終期間隔離（実装済み）

`src/stock_prediction/splits.py` は、2016〜2024年を開発期間として固定し、2020〜2024年を
各1年の検証期間にする拡大型ウォークフォワード分割を生成する。同じ `signal_date` の全銘柄を
同じ役割へ割り当て、公式取引カレンダー上の取引日数でパージする。既定の4取引日は、入力内の
最大ラベル期間以上であることを実行時に検査し、ラベルが検証開始へ達する学習候補も除外する。

2025〜2026年内の隔離開始日・終了日は `configs/splits.json` で選択できる。選択した期間から
外れる行や年境界をラベルが跨ぐ行は開発へ戻さず、`out_of_scope` として理由と件数を残す。
Notebook用の `build_walk_forward_splits` は `iloc` 用の位置配列を返し、CLI
`stock-splits` / `python -m stock_prediction.splits` は年別週次Parquetから日付単位の分割定義と
監査manifestを保存する。実行例は [実行手順書](docs/RUNBOOK.md)、境界・列・出力仕様は
[時系列分割仕様](docs/SPLITS.md)、実装判断と検証結果は
[実装計画](docs/IMPLEMENTATION_PLAN.md) を参照する。

最終評価期間を一度見た後の設計変更は、その期間を未使用へ戻さない。現在は実データ週次学習表が
未生成のため、実fold件数とcoverageは未検証であり、合成データの分割テストを投資成績と解釈しない。

## 21. 定数・モメンタム・線形基準モデル（実装済み）

## 23. 約定制約・コスト・上場廃止を含む売買バックテスト（実装済み）

`src/stock_prediction/backtest.py` は、シグナル日終値後の予測順位から上位Nを選び、次の東証取引日の
未調整始値で買い、主設定では評価日の未調整終値で売る。買い注文はその始値で未約定なら失効し、
売り注文は値幅制限、停止proxy、価格欠損、参加率制約で約定できない限り後続取引日へ繰り越す。
評価日翌取引日始値での決済も設定で切り替えられる。

株数は利用可能現金、売買単位、シグナル時点までの過去20取引日売買代金中央値に対する参加率上限で
切り下げる。当日始値注文のサイズ決定に、当日の終値・出来高・売買代金を使わない。片道コストの
初期値は、ユーザー確認済みの手数料5bps、半スプレッド5bps、スリッページ10bpsである。これは
一般的な市場標準ではなく、`configs/backtest.json` で個別に変更し、manifestへ保存する研究仮定である。

確定上場廃止イベントと1株当たり清算価値が入力されれば、その実条件で保有を清算する。保有中の
上場廃止に清算値がなければ、主設定はエラーとして結果を確定しない。全損は明示的な感度分析設定で
のみ選べ、価格欠損や銘柄マスターからの消失を上場廃止と推測しない。調整係数がある日は保有株数を
変更し、注文、約定、保有、コーポレートアクション、日次資産、週次ターンオーバーを別成果物に残す。
全期間に加えて、年別の収益、ボラティリティ、Sharpe、最大ドローダウン、コスト、ターンオーバーも
保存する。

Notebook用の `backtest_portfolio` とCLI `stock-backtest` /
`python -m stock_prediction.backtest` は同じ中核処理を使う。実行例は
[実行手順書](docs/RUNBOOK.md)、入力契約、数式、未約定・上場廃止規則、制限は
[売買バックテスト仕様](docs/BACKTEST.md)、判断と検証結果は
[実装計画](docs/IMPLEMENTATION_PLAN.md) を参照する。

現在の実データには、同一スナップショットから生成した週次候補表、予測成果物、確定上場廃止清算表が
ないため、実データ投資成績は未検証である。合成データの既知値テストを将来利益の根拠として扱わない。

## 24. 全工程の再実行と実験レポート（実装済み）

`src/stock_prediction/experiment.py` は、保存済みの不変rawスナップショットを入力として、前処理、
TOPIX正規化、特徴量、週次日程、時点ユニバース、決算除外、週次学習表、パージ付き分割、基準モデル、
独立予測評価、コスト込みバックテストを依存順に再実行する。CLI `stock-experiment` /
`python -m stock_prediction.experiment` とNotebook用 `run_experiment` は同じ処理を使う。

J-Quantsからの取得は一括実験の前段として分離する。同じ日付を後日再取得しても訂正により同一入力とは
限らないためである。実験は価格・補助データそれぞれのsnapshot ID、manifest SHA256、manifest内に
宣言されたSHA256集合の識別子を保存し、各工程は実際に読んだファイルのSHA256を個別manifestへ
残す。`data/raw/` は変更せず、TOPIXの `Date` / `C` は検査後に `data/interim/` の `date` / `close`
派生ファイルとして保存する。

実験設定の例は `configs/experiment.example.json` にある。rawスナップショットのプレースホルダーを、
価格とカレンダーを持つsnapshot、およびTOPIX・時点銘柄マスター・決算予定・財務実績を持つsnapshotへ
置き換え、まず `--validate-only` で全入力と全工程設定を検査する。出力はrun IDごとに次へ分離される。

保存済みbaselineの `input20161101-20261001_baseline-r001` は、出力期間ではなく固定raw入力の
coverageと設定revisionを表す。同期間を再取得したrawは `snapshot01`、`snapshot02` のように区別し、
実際の実行日時と一致しない `manual_YYYYMMDD_HHMMSS` はrun IDに使用しない。

- `data/interim/experiments/<run-id>/`：監査済み価格と正規化TOPIX
- `data/processed/experiments/<run-id>/`：特徴量、日程、ユニバース、決算判定、週次表、分割
- `artifacts/experiments/<run-id>/`：モデル、予測評価、バックテスト成果物
- `reports/experiments/<run-id>/`：最上位・工程別manifest、解決済み設定、Markdownレポート

既存run IDは上書きも自動再開もしない。失敗・`Ctrl+C` では後続工程を実行せず、完了済みの個別成果、
停止工程、例外、最終更新時刻を最上位manifestとレポートへ残す。バックテストに未決済建玉が残れば
実験状態も `incomplete` とし、成功に見せない。

現行のmodelingは2016〜2024年だけから2020〜2024年の開発検証予測を作る。そのため実験レポートの
予測指標と売買指標も開発期間の比較であり、2025〜2026年の最終バックテストではない。
上流工程で隔離候補表を準備する場合も、`final_period_used_for_model_selection=false` と
`final_period_evaluated=false` を最上位manifestへ保存する。最終期間用の学習・推論工程が別途実装され、
開発期間で設計を固定するまでは、実験CLIが隔離期間を評価へ流さない。詳細なコマンド、Notebook例、
出力確認方法は [実行手順書](docs/RUNBOOK.md) を参照する。
